# FleetPilot Drivers — integration readiness assessment

Assessment date: October 25, 2026. Documentation only. Drivers source baseline: `ae04cb215651aeea5debb95173d23c733a74aa70`, branch `feature/drivers-ui-redesign`, [Draft PR #99](https://github.com/shirimov/fleetpilot-tms/pull/99). Refreshed `origin/main`: `df1796ad40d7d22dc400338a742170430e49eb0c`.

## Executive summary

**Prepare one combined integration candidate; do not deploy Drivers independently into an existing Fuel environment.** Reuse FleetPilot's Docker host, PostgreSQL service, private-volume design, release/migration tooling and backup infrastructure. Drivers does not need a separate production database, app deployment, identity store or second Safety system. The existing stack is a suitable foundation, but its current configuration does not satisfy Drivers' production gates.

Drivers is five commits ahead of current main and zero commits behind. It changes 77 paths, adds two migrations, and retains all 47 main migration files byte-for-byte. Current main has 47 committed migrations; Drivers has 49. These are **repository counts, not verified applied production migrations**.

The active Fuel candidates have five additional migrations and overlap Drivers in `prisma/schema.prisma` and shared navigation/shell files. A read-only, per-file three-way analysis detects a schema conflict. The combined current Fuel/Drivers migration union would contain **54 files**, with no shared migration-path checksum mismatch in the inspected refs. A clean GitHub merge against main would not prove compatibility with these local Fuel changes.

The implementation can be reviewed/integrated before future Safety is built. Production approval must wait for the five operational blockers below and tests of the **combined** candidate. Do not wait for or blindly merge every old Accounting/QuickManage/Task branch: many are behind main or stacked on unmerged dependencies. Select a canonical release baseline with their owners first.

Specific remaining work is deployment/configuration wiring, scanner acceptance, legacy migration tooling/procedure, coordinated recovery and integration-test coverage. No additional Drivers feature development is recommended now.

## 3. Five deployment blockers

### B1 — Durable encrypted documents and keys

**Exists:** shared private volume, non-root app, private directory initialization, Drivers authenticated encryption/keyring and guarded private APIs. **Missing:** explicit Drivers environment/secret forwarding, verified durable volume ownership/mounts/capacity, production key escrow/rotation ownership, key IDs linked to recovery sets, and integrated image-level storage tests. The real-review overlay is intentionally read-only.

**New coding:** deployment/test wiring, not a new storage service or database. **Configuration:** volume namespaces, 1001 ownership, secret injection, least-privilege worker identity and encryption/backup policy. **Approval:** required before provisioning, introducing real secrets, mounting real data or changing access. **Order:** first shared infrastructure gate; establish before scanner release/legacy migration.

### B2 — Real ClamAV and signatures

**Exists:** bounded Unix-socket adapter, quarantine, scan/audit records and fail-closed production behavior. **Missing:** verified daemon/signatures, update path, shared socket mount/permissions, resource limits, readiness/age alerts and real clean/EICAR/encrypted-content/scan-limit acceptance tests. Protocol-simulator results establish application behavior only.

**New coding:** Compose/runtime/socket/health wiring and acceptance automation. **Configuration:** reuse an approved scanner if one is later verified; otherwise add the minimal scanner/updater capability, with controlled signature-update egress and no public clamd port/provider credentials. Keep the socket on a separate private runtime mount, outside the recursively chowned/backed-up document volume. **Approval:** required before installation, network/resource changes or real-file scans. **Order:** after B1, before any document release/migration.

### B3 — Legacy document migration

**Exists:** retained legacy versions, UNSCANNED defaults, append-only replacement/date history and clean/encrypted download gates. **Missing:** approved inventory/provenance, repeatable dry-run/resume tooling for historical scan/encryption, verified per-version recovery/receipt handling and an agreed exception process. No automatic historical migration or quarantine-release tool exists.

**New coding:** a narrowly reviewed offline migration/reconciliation tool if existing originals must remain downloadable; this is a specific operational gap, not another profile feature. Re-uploading a clean replacement preserves the original but does not make old versions production-readable. **Configuration:** isolated rehearsal copies, scanner, keys, mapping/retention policy and maintenance barrier. **Approval:** required for any real inventory/data access and separately for file/metadata writes. **Order:** define requirements now; rehearse only after B1/B2 and a usable B5 recovery set; execute only after final approval. Do not weaken fail-closed checks to bypass it.

### B4 — Reminder scheduling and monitoring

**Exists:** per-company policy, CLI, UTC stages, optional MVR review interval, unique deduplication, audited history, last-success/failure fields; Fuel has reusable job/lock/monitor patterns. **Missing:** packaged Drivers runtime, per-company schedule, approved service DB role, restart/non-overlap policy, alert routing, disabled-policy heartbeat semantics and shared maintenance coordination.

**New coding:** small worker/service/test and monitor wiring. `Dockerfile` runner lacks the source/CLI runtime; the existing full-source migrator image is a reuse candidate, but its `USER node` differs from the app's explicit 1001 identity. Do not assume file ownership or reuse Fuel's scoped DB credentials. Reminder-only jobs need no provider credentials, file keys or file volume; storage health/backup jobs need separately scoped access. **Configuration:** explicit company IDs (not OperatingGroup IDs), approved policy, default-off gates, controlled schedule and monitored exit/status. Do not run both a Fuel loop and a duplicate timer for the same Fuel business job. **Approval:** required before enabling schedules/policies/real alert delivery. **Order:** prepare after baseline selection; enable Drivers reminders last, after file reconciliation and acceptance. External delivery remains absent/disabled.

### B5 — Coordinated PostgreSQL, files and key recovery

**Exists:** age-encrypted whole DB/private-volume backup, matched-set checksum/completion verification, Drivers encrypted scoped backup/new-destination restore, and Fuel's isolated restore-probe/off-host/monitor patterns. **Missing:** one all-writer maintenance protocol, release/migration/key-reference manifest, independently verified off-host/escrow availability, retention approval and a joint full-system restore drill.

**Critical blast radius:** `restore-staging.sh` uses `pg_restore --clean`, deletes the entire private-volume contents and restarts the application. It is not a Drivers-only recovery tool. Baseline backup/deploy does not pause every writer; Fuel's backup wrapper pauses app/Fuel worker, not a future Drivers worker or Samsara cache writer. Existing recovery scripts do not establish Drivers key/scan/authorization acceptance. Shared backup retention prunes completed sets, which is distinct from preserving active document versions and must be approved for all modules.

**New coding:** extend existing orchestration/acceptance and record a recovery manifest; do not create an unrelated second full-backup system. **Configuration:** halt all relevant writers under a common barrier, match DB/files/keyring/age identity/Drivers backup-key reference and financial encryption-key dependencies; retain immutable originals and orphan evidence appropriately. Scoped Drivers backups omit unreferenced orphans; the whole-volume backup can preserve them. **Approval:** required before accessing real backups/keys or restoring anything. **Order:** design alongside B1; prove recoverability before B3 or any real rollout. Use a fresh isolated restore target, never the current Fuel environment.

## 5. Security and integration acceptance criteria

- OWNER/ADMIN manage only the selected company's authorized Drivers; verified Employee-based operational readers retain read-only access. Manager/Safety/Admin document access and dispatch compensation/CDL/emergency redaction match the existing contract. Inactive/revoked/foreign-company identities fail on every route/history/version, including direct URLs and changed active-company sessions.
- Company/truck/load/settlement/financial-allocation/provider IDs remain unchanged through upgrade/restore. Employment status does not become duty status; historical truck/company attribution is not rewritten from current assignment. Driver DELETE stays non-destructive. No duplicate drivers, financial expenses, accounting posts or new provider mappings are created as a side effect.
- Private files stay outside served paths, encrypted with available historical keys, owned correctly and durable through container replacement. Real clean/EICAR/error/timeout/encrypted/limit/tamper cases behave as approved. Failed scans remain quarantined; no unscanned historical download is silently permitted. Validate scanner update age/monitoring with real infrastructure under approval.
- Joint reminders respect explicit company policies, current versions, MVR dates, UTC windows, duplicate prevention, disabled states and scheduler retries. Failures are visible; stale success does not report healthy indefinitely. External notifications remain disabled unless separately implemented and approved.
- Recover a matching **full** PostgreSQL/private-files/key set into a new isolated target; verify current/historical document bytes, quarantine, audits, all tenant/role boundaries and retained financial/provider state. Wrong/missing keys, incomplete sets and missing/corrupt files fail safely. Counts distinguish physical files, DB versions, scan rows and global orphans. No automatic orphan/history deletion.
- Validate Finance permissions and private response headers across Fuel/QM/Samsara plus Drivers navigation. Existing Finance read-only guards do not substitute for a whole-app read-only rehearsal environment. Do not run test fixtures against real-data review databases.
- Run exact combined-candidate Prisma validation/generation, TypeScript, targeted lint, regression suites, authenticated browser flows and production/container builds. Report baseline lint/environment failures separately. Prior per-branch passes and GitHub `mergeable` are insufficient.

## 6. Rollback and final gates

Prefer a reviewed forward fix with schedules disabled/maintenance mode enabled. Additive schema changes are not permission to drop data. **Do not run Phase 2/old main against newly encrypted Drivers files:** the old app can neither enforce the new scan policy nor read the new envelopes correctly. Any rollback requiring a prior release must restore a coordinated whole-system DB/files/key set into a new environment and obtain all affected module owners' approval; review post-backup activity and financial reconciliation before cutover. Never invoke the destructive shared restore as a single-driver repair.

Production gates: approved canonical release and migration ledger; resolved schema/shell/auth conflicts; verified durable storage and escrow; real scanner/signatures; approved legacy migration outcome; operational schedules/monitoring; coordinated recovery/off-host/retention proof; passing joint acceptance; documented owner sign-off, maintenance window and rollback decision authority. **Current decision: not cleared for production deployment.**
